# Software factory

How work flows through quat-3d without a human in the loop for routine
steps. The owner sets direction (ROADMAP.md, requests); agents find
problems, fix them, review each other and merge what is green.

```
 hourly Scanner ──opens──▶ GitHub issues (label: factory)
                                 │
 Orchestrator (live session) ◀───┘ triages, verifies, groups
        │ fans out ──▶ Worker agents (one worktree + feat/<id> branch each)
        │                    │ push
        │ opens PR ◀─────────┘
        │        └──▶ Reviewer session (one per PR) ──comments──▶ PR
        │ addresses review, CI green ──▶ merge (merge commit) ──▶ issue closed
```

## Roles

### Scanner (hourly, its own session)
- Works on the latest `master`, read-only: never pushes, never edits files in
  the repository, never opens pull requests.
- Each run picks the **next area in rotation** (below) so successive runs
  cover the whole engine; it records the area it scanned in its run summary.
- Looks for real defects: crashes, hangs, memory/lifetime bugs, Vulkan
  synchronisation or validation errors, data races, unchecked untrusted input,
  path traversal, broken invariants, determinism breaks, performance
  pathologies, and violations of CLAUDE.md rules. Each finding must be traced
  through the actual code path; where cheap, demonstrated with a compile check
  or a tiny test.
- **Before opening an issue**, searches open and recently closed issues for
  the same problem (and `docs/audit/`) — no duplicates.
- Opens at most **5 issues per run**, using the template below and the labels
  `factory`, `bug` (or `rule`/`perf`), one `severity:*` and one `area:*`.
- If it finds nothing solid, opens nothing. Precision over volume.

Area rotation: `rhi` (device, allocator, pipeline cache, render graph,
descriptor buffers) → `renderer` (passes, shaders) → `scene` (ECS, codec,
scene files, glTF) → `physics` + `nav` + `ai` → `remote` + `tools/quat-mcp` →
`app` + `editor` → `terrain` + `audio` + `net` → `build` (CMake, CI, vcpkg,
platform code) → back to `rhi`.

### Reviewer (one session per pull request)
- Created by the orchestrator when a PR opens; reviews the full diff against
  CLAUDE.md, ROADMAP.md scope and docs/LEARNINGS.md.
- Posts one review on the PR: inline comments for concrete defects (with a
  failure scenario and a suggested fix), a summary comment with an overall
  verdict. Severity on every comment: **blocking** (bug, rule violation, missing
  test for new behaviour) or **non-blocking** (nit, follow-up).
- Never pushes, never approves, never merges. When asked to re-review after
  fixes, reviews only what changed and resolves threads that are addressed.
- Every comment ends with the attribution footer:
  `---` / `_Generated by [Claude Code](https://claude.ai/code)_`.

### Orchestrator (the live session, plus its scheduled check-ins)
- Each check-in: read new `factory` issues → verify each (reject with a
  comment if not reproducible from the code) → label `triaged` → group related
  ones → spawn worker agents (up to the agent budget in CYCLE.md) → comment on
  each issue with the worker branch.
- Opens a PR per worker branch (or per cycle where items are interdependent),
  `Fixes #N` in the body, creates its Reviewer session, addresses blocking
  review comments (or sends them back to the worker), merges once CI is fully
  green and no blocking comment is open (CYCLE.md merge rule).
- Records process failures in docs/LEARNINGS.md.

### Worker (worktree agent)
- Exactly as in CYCLE.md's brief template; the brief names the issue(s), and
  commits reference them (`[ID] … (#N)`).

## Issue template (Scanner)

```markdown
**Severity:** high | medium | low      **Area:** <area>
**Where:** path/file.cpp:LINE (function)

### What is wrong
<one paragraph>

### Failure scenario
<concrete inputs/state → wrong result / crash / hang>

### Evidence
<the code path traced, with file:line references; test or compile output if run>

### Suggested fix
<specific>

---
_Generated by [Claude Code](https://claude.ai/code)_
```

## Labels
`factory` (opened by the scanner) · `bug` / `rule` / `perf` ·
`severity:high|medium|low` · `area:<area>` · `triaged` (orchestrator verified)
· `in-progress` (a worker owns it) · `wontfix` (with a reason).

## Limits
- Scanner: ≤ 5 issues/run, hourly. Reviewer: one review pass per push.
- Agents never merge non-cycle PRs from people, never force-push, never push
  to `master` directly, never skip or disable tests to get green.
